## 一、目标与非目标

D10 要解决的问题：**当前 Docking 的全部几何证据都来自"单显示器、96 DPI、交互式
桌面"这一个环境组合**。浮动窗口的跨屏定位、混合 DPI 下的坐标往返、显示器缺失或
排列变化后的恢复、最大化／还原过渡期的 Bounds 持久化，都没有被任何门禁证明过。
D10 的产物应当是"这些行为在此环境矩阵下成立（或明确不成立）"的可执行结论，而不是
新的几何策略堆叠。

非目标（属于本契约的禁止项）：

- **不**把 D9 关闭后遗留的未判定失败（ADR-010 §11.4）当作 D10 的前提或"已解释"；
  若 D10 的门禁复现它，必须按 §11.8 的判据重新指名与判定。
- **不**修改 ADR-005/007/008/009/010 已冻结的模型、宿主、持久化与生命周期语义。
  本契约若需要新的持久化字段或新的模型语义，必须以**显式修订条款**提出并由用户裁决，
  不得顺手改。
- **不**在 **D10-C 获得修复授权前**修改 `DockFloatWindow`、`DockWindowRootHost`、
  `DockWorkspaceCoordinator` 的坐标转换或持久化格式。§二 列出的事实是"待验证风险"，
  **不是已证实缺陷**；契约虽已冻结（O-2/O-4/O-5 的行为规则成立），但把它们写进产品代码
  仍需 D10-B 的失败证据与 D10-C 的单独授权。
- **不**引入新的窗口管理框架、不重构投影层、不动场景命令历史与快捷键路由。

## 二、现状基线核对（D10 契约必须绕开的事实，全部当场可复现）

1. **整个 Docking 层没有任何屏幕枚举**。
   `grep -rn "Screens\|Screen\." src/Nova.UI.Avalonia/Docking src/Nova.Editor.Views/Docking`
   仅命中 `PixelPoint screenPoint`、`ScreenPoint` 属性与 `HasScreenPoint` 之类的
   **点**用法，**0 处** `Screens` 集合或 `Screen` 对象访问。结论：现在不存在
   "这个窗口属于哪块屏 / 这块屏还在不在 / 它的工作区是什么"的任何概念。
2. **几何单位是"当前窗口自己的 RenderScaling"**。
   `DockFloatWindow.CaptureBounds()`（`src/Nova.UI.Avalonia/Docking/DockFloatWindow.cs:161-171`）
   把 `Position`（像素）除以 `_window.RenderScaling` 存成模型值；
   `ToPixelPoint()`（同文件 :173-179）在应用时再乘回**当时的** `RenderScaling`。
   该文件 :43 的注释自己写着 "best effort under mixed DPI"。因此同一份持久化几何在
   不同 DPI 的屏幕上被重新解释，往返误差不被任何代码约束。
3. **tear-off 的坐标来自"主窗口 scaling ÷ 屏幕点"**。
   `DockWorkspaceCoordinator.cs:1570-1582` 用 `e.ScreenPoint / scaling`（scaling 取
   自主 `TopLevel` 的 `RenderScaling`）加上固定 `640×480` 生成浮动根；
   `ClampTearOffBounds`（:1722 起）**只兜尺寸非法时的默认 640×480**，不做任何
   "是否落在某块屏内"的钳制。跨屏 tear-off 会混用两个屏的 scaling 口径。
4. **模型侧只有数值合法性，没有屏幕概念**（这是 ADR-007 冻结的 D6-B 语义，不是缺陷）。
   `DockWorkspaceValidation.cs:49/52` 只检查 `Bounds.IsValid` 与
   `RestoreBounds.IsValid`；`DockBounds` 是 `readonly record struct (double X, Y,
   Width, Height)`（`src/Nova.UI.Core/Docking/DockBounds.cs:7`）。
5. **持久化几何是纯数字**。Schema v3（ADR-008 定义、ADR-009 扩展 `tabs.hidden`）
   的浮动根写入 X/Y/Width/Height、`maximized` 与 `RestoreBounds`，
   **没有屏幕身份、没有 DPI、没有工作区引用**。因此"恢复到原来那块屏"目前只能靠
   数值巧合，缺失那块屏时也没有信息可用于重定位。
6. **已知的过渡期时序事实**（历史结论，非本次新证）：Windows 上 Avalonia 会先报
   位置／尺寸、后更新 `WindowState`，D7-D 因此给 `IsMaximized` 补了原生 `IsZoomed`
   判据（ADR-008 记录）；ADR-010 §11.3 另留有一条已指名但此后未复现的
   `Unmaximizing_…` 失败（磁盘浮动 X 读回 0 而非 180）。
7. **真实进程门禁的桌面假设**：现有 RP/LM 真实输入门禁全部依赖单显示器 96 DPI 桌面
   的前台窗口与物理像素坐标（`SetCursorPos` + `mouse_event`，UIA 读取）。屏幕数量或
   DPI 改变时，这些门禁**自身**的前提也会失效，所以 D10 必须先区分"被测行为失败"与
   "门禁假设不成立"。

以下两条是 D10-A 裁决后当场补入的代码事实（均由 `grep`/`Read` 复现，非推测）：

8. **进程是 Per-Monitor V2 DPI 感知的**（`src/Nova.Editor.App/app.manifest:6-7`：
   `dpiAware = true/pm`、`dpiAwareness = permonitorv2,permonitor`）。含义有两面：
   好的一面是 `TopLevel.RenderScaling` 在不同 DPI 的屏上**确实会变化**，因此不存在
   "系统位图虚拟化掩盖了问题"这种解释；坏的一面是一旦几何被以错误的缩放口径写入
   模型，Windows 不会替我们把它修正回来。因此 D10 的门禁必须按真实 per-monitor 缩放
   来判定，不能把"看起来正常"归因于 DPI 虚拟化。
9. **拖放屏幕点的换算口径跟随"源窗口的 TopLevel"**：
   `DockDragController.TryGetScreenPoint`（`src/Nova.UI.Avalonia/Docking/DockDragController.cs:861-887`）
   用 `TopLevel.GetTopLevel(_root)` → `top.PointToScreen(...)` 与
   `scaling = top.RenderScaling`（:879），再把这个 scaling 随
   `DockDragEventArgs.RenderScaling`（`DockDragContracts.cs:45/69`）交给协调器；
   `DockWorkspaceCoordinator.cs:1575-1576` 直接采用该值。因此跨屏 tear-off 用的是
   **拖放起始窗口所在屏**的缩放，而不是指针当前所在屏的缩放——与 §二 3 是同一类
   口径问题，但发生在另一个位置（拖动过程中，而不是 tear-off 之后）。

以下一条不是裁决前的基线，而是 **D10-B 第二轮当场测出**的代码事实（可由 §十·一/§十·二
的真实进程门禁复现）：

10. **模型里的 Width/Height 既不是客户区尺寸，也不是真实窗口外框尺寸**。
    `CaptureBounds`（`DockFloatWindow.cs:161-171`）只把 `Position` 除以 scaling，
    **Width/Height 直接取 `_window.Width/_window.Height`**（Avalonia 的请求尺寸），
    从不读回平台真正给出的外框矩形。实测：播种 640×480 → 真实窗口矩形 656×519
    （DM-RP-01/02）；播种 2960×1852 → 真实窗口矩形被 Windows 自身限制为 2580×1620，
    而磁盘值仍是 2960×1852（DM-RP-03）。也就是说"持久化的尺寸"和"窗口实际占的尺寸"
    是两个量，程序也从不因为平台的限制而更新模型；这正是 O-3.1"所有操作数必须处于
    明确且一致的坐标单位体系"目前不成立的具体形态之一。

## 四、O-1…O-6 裁决结果（已冻结的行为契约；2026-10-27 用户逐项裁决）

> 措辞口径：**"冻结的是行为契约"不等于"现状已实现"**。以下每一条都是 D10-B 用来
> 衡量现状的准绳；偏差按第九节的流程记录，而不是靠改契约来消除。

### O-1 持久化是否记录屏幕身份 → 接受 (A)：暂不存储屏幕身份

- 继续使用 Schema v3 的**纯几何**持久化，不引入屏幕 ID，也**不**因进入 D10 就自动
  启动 Schema v4 迁移。
- 理由：应先验证"所需的恢复行为能否仅靠现有几何 + 确定性运行时恢复策略满足"。新增
  持久化字段必须由**实际验收证据**驱动，而不是因为多显示器场景尚未验证就提前引入。
- D10-B 必须覆盖四种情况：原窗口所在显示器仍存在、显示器排列变化、原显示器断开、
  混合 DPI 下重启恢复。
- **升级条件**（唯一允许提出 v4 的入口）：D10-B 证明仅凭几何无法满足本契约的定位与
  可见性规则，**且**运行时恢复策略也无法可靠解决时，才可提出 Schema v4 方案；提案
  必须以实际失败案例说明新增字段解决什么问题，**不得直接扩大迁移范围**。

### O-2 原显示器不可用时的恢复 → 接受"确定性钳制至可见工作区"

按顺序适用的五条规则：

1. 原几何**完整落在**当前任一显示器工作区内 → 保留该位置，**不得**因为缺少屏幕身份
   而无条件移动到主屏。
2. 窗口**部分越界** → 选择与原窗口矩形**交叠面积最大**的当前工作区，并钳制进去。
3. 与所有当前工作区**均无有效交叠** → 恢复到**主显示器**工作区内。
4. 窗口尺寸超过所选工作区可容纳尺寸 → **先按规则缩小，再钳制位置**。
5. 恢复结果必须**可见、可操作**；不得静默恢复到所有显示器之外，**不能只保证模型里的
   Bounds 数值合法**（这是"用户可见结果必须可被观察"的既有纪律在本阶段的落点）。

两条前提性约束：

- 这是**明确的恢复策略**，不代表当前代码已实现；D10-B 首先验证现状并记录具体偏差。
- **不得**仅因为没有持久化屏幕身份，就假设某个现有矩形"属于已断开的显示器"。当前
  无法可靠识别这一事实；恢复算法只能依据**当前可见工作区与窗口几何**作确定性决策。

### O-3 几何单位与 DPI 转换 → 接受"行为契约先冻结，存储编码由 D10-B 证据决定"

裁决明确**不批准**两件现在可能想做的事：不把未经验证的现有四个数值直接宣布为 DIP；
不启动"像素 + DPI 元数据"的 Schema v4。冻结的外部行为五条：

1. 几何运算中的**所有操作数必须处于明确且一致的坐标单位体系**；**禁止**直接混合物理
   像素与 DIP。
2. 屏幕指针坐标必须**根据其真实坐标语义解释**，**不得**直接使用主窗口的 `RenderScaling`
   对所有屏幕坐标做统一换算（§二 3 的 tear-off 与 §二 9 的拖动换算都落在这条下）。
3. DIP 与像素之间的转换**由相应窗口宿主边界负责**，采用**与目标窗口及实际操作相符**的
   缩放信息。
4. 跨 DPI 移动或重启恢复时，窗口尺寸必须符合约定的**逻辑尺寸**行为；恢复后的窗口必须
   遵守 O-2 的可见性契约。
5. 当前 Schema v3 **仅作为 D10-B 的现状基线**，不预先认定其足以支持所有新场景。

D10-B 用**实际的目标显示器缩放配置**测量当前位置、窗口尺寸与恢复结果；若现有格式无法
满足契约，再提出**最小** schema 变更，并分别说明是否需要记录 DPI、显示器身份，或者两者
都不需要。这样既避免过早迁移，也不把当前未定义的坐标换算默认为正确。

### O-4 Tear-off 按哪个显示器定位、如何钳制 → 接受"按指针所在显示器 + 可见性钳制"

冻结规则五条：

1. 使用拖放指针**实际所在**的显示器，而不是主窗口所在的显示器。
2. 默认浮动窗口尺寸 **640×480 是 DIP**，不得把这两个数值当成物理像素。
3. 使用**目标显示器的工作区**计算可用位置，**不得**以主窗口的缩放系数替代目标显示器的
   缩放信息。
4. 窗口尺寸超过目标工作区可容纳范围 → 缩小到可容纳尺寸，再钳制位置。
5. 无法可靠确定指针所在显示器 → 使用 O-2 定义的安全回退策略。

裁决确认这是**产品行为的明确化**，意味着现有 tear-off 行为可能需要改变；但 D10-B 先
验证现有实现及其失败边界，**在 D10-C 获得修复授权前不修改** `DockWorkspaceCoordinator`
或相关窗口代码。

### O-5 最大化／还原期间何时允许写入 `RestoreBounds` → 接受严格稳定状态门禁

**只有同时满足以下四条**，才允许把观测到的几何作为新的 `RestoreBounds` 持久化值：

1. 窗口 `WindowState` 已确认是 **Normal**，而非 Maximized 或 Minimized。
2. 可用的宿主或原生窗口状态**没有**表明窗口仍处于最大化状态（现状事实：Windows 上
   Avalonia 先报位置／尺寸后更新 `WindowState`，故需原生 `IsZoomed`，见 §二 6）。
3. **已越过状态转换的中间帧**，窗口几何稳定——不再是最大化矩形，也不是尚未完成还原
   的矩形。
4. 捕获与保存**只使用**通过以上检查的稳定几何；否则**保留此前有效的 `RestoreBounds`**。

稳定性必须由**实际状态与几何观测共同**确定：不能只依赖一次 `WindowState` 检查，也不能
仅凭某个 Bounds 数值"看起来合理"就保存。D10-B 需验证最大化、还原、快速连续状态切换
以及进程重启恢复；判定稳定的具体事件边界与观测方式由现有宿主能力与测试证据确定，
**不得为了通过测试而引入任意固定延迟**。

### O-6 自动化与人工验收边界 → 接受，且真实环境证据与 headless 证据必须分开记录

| 验收对象 | 允许的验证方式 | 能得出的结论 |
| --- | --- | --- |
| 纯几何规则、矩形钳制与恢复策略 | Headless 单元与集成测试 | 证明算法与状态逻辑 |
| 窗口宿主的 Bounds 转换、缩放与状态事件 | 真实控件测试；必要时辅以模拟屏幕布局 | 证明受测宿主逻辑，**不等于**真实混合 DPI 验证 |
| 多显示器、不同 DPI 下的实际窗口移动与重启恢复 | 配置正确的交互式 Windows 桌面上的真实进程测试，或有证据的人工测试 | **只**证明实际执行过的显示器拓扑与 DPI 组合 |
| 无人值守、无交互桌面环境 | 单列为未验证项，除非实际执行并保存有效证据 | **不得**根据 headless 测试推断 |

每个真实环境案例必须记录（缺一即视为记录不完整）：门禁 ID、操作系统与构建信息、
显示器数量与排列、主显示器、每台显示器的分辨率与缩放比例、操作前后的窗口 Bounds、
预期与实际结果、复现步骤、通过／失败结论，以及所需的日志或截图。

真正的混合 DPI 桌面，本阶段必须如实记录为**未验证**。

## 六、变更边界（D10 明确不包含）

- 不改模型语义：`DockBounds` 仍是纯数字；屏幕概念只允许存在于宿主与验证层，
  除非 O-1 (B) 被裁决采纳。
- 不改持久化策略：写入时序、去重、抑制、退出快照仍归 ADR-008/009；D10 只谈几何
  如何被解释与恢复。
- 不改布局历史语义：Undo/Redo 仍按 ADR-010，O-6（不恢复面板内部内容）仍是产品限制。
- 不做跨进程窗口、嵌套浮动、每浮动根多窗口（ADR-007/010 既有排除项照旧）。
- 不做 Linux/macOS 的多屏验证；本契约范围限于 Windows 桌面（与现有真实进程门禁一致）。
- 不在契约批准前提交任何实现。
- **D10-B 的执行边界（裁决）**：本阶段目标是"建立可复现的环境矩阵、验证现状、确定后续
  实现工作的必要性"，**不是**立即重写 Docking 坐标系统。可以新增**有明确边界**的测试与
  证据文档；任何生产代码修改都必须先记录失败证据、明确修复范围，并**单独进入实现阶段**
  （D10-C）申请授权。**不得顺手修改** `DockFloatWindow`、`DockWindowRootHost`、
  协调器坐标换算或持久化格式。

## 七、后果与风险

- **D10 的结论可能是"现状可接受"**：若 E2/E3 门禁全部通过，则 §二 列出的风险被证明
  为"未被约束但恰好正确"，本阶段只需补门禁与文档，不需要产品改动。这仍是有价值的
  交付，不能因为"没改代码"就当作未完成。**但该结论的适用范围只能覆盖实际执行过的
  拓扑与缩放组合**（O-6 第一行/第三行）：在本机只有 E1 的条件下（§九·二），
  任何"E2/E3 可接受"的表述都无从成立，只能写"未验证"。
- **门禁可能暴露真实缺陷**：混合 DPI 往返误差、跨屏恢复丢失、越界不可见都是合理预期
  的候选发现；届时按既有纪律——发现即修复根因、不用切平台/关特性绕过、并把失败与
  修正都留进记录。
- **测试基础设施风险**：现有真实输入门禁把物理像素坐标与前台窗口假设写死在单屏
  （§二 7）。多屏/DPI 改变会让门禁自身先失败，因此 D10-B 必须先做门禁前提自检
  （屏数/缩放不满足预期时 `Assert.Inconclusive` 并打印实际环境），否则会把基础设施
  问题误报成产品缺陷。
- **验收口径风险**：D10 可能只能覆盖"人工可搭建的部分环境"。届时封印记录必须写明
  哪些 E×S 单元格是实测、哪些是豁免、哪些是人工，且**不得把部分覆盖写成 DPI 支持**。
- **残余风险延续**：ADR-010 §11.4 的未指名 Release 失败与 §11.3 的浮窗过渡失败
  继续按"未判定/复验事实"保留，D10 不继承也不消解它们。

  构造混合缩放。按 O-6 的划分，这三格只能记为**未验证**；要推进需要用户实际接入
  第二显示器（或允许改变本机缩放设置——这属于对用户环境的修改，需明确授权）。
- 因此 D10-B 在本机的**可交付内容**限于：（a）几何契约的 headless/真实控件门禁
  （用受控的"模拟屏幕布局"喂给被测算法，验证 O-2/O-4 的规则本身，但结论只到
  "受测宿主逻辑"，不等于真实混合 DPI 验证）；（b）现有 tear-off 与 `RestoreBounds`
  路径的**现状偏差测量**；（c）真实进程门禁的**环境前提自检**（屏数/缩放不满足预期时
  `Assert.Inconclusive` 并打印实际环境，避免把基础设施假设失败误报成产品缺陷）。
- **三项在两轮之后的交付状态**：（a）已交付 DM-B01/B02/B03 三条 headless 门禁 +
  四条真实进程门禁；（b）已交付，tear-off、恢复、部分越界、超大尺寸、最大化/还原快速
  切换五种路径都有实测数字（§十·一/§十·二）；（c）已交付——每条真实进程门禁都带
  "可观察前提"断言（§五·二 第 3 列），其中 DM-RP-03 还额外把"平台自己限制窗口"与
  "产品缩小模型"分成两条判据。E2/E3/E4 依旧只能记为未验证。

### 九·三 D10-B 的结束标准（裁决原文的三问）

D10-B 的结束标准**不是**必须判定现状有缺陷，而是用可复现证据回答：

1. 当前持久化几何能否满足混合 DPI 的可见性与尺寸契约（O-2 + O-3）；
2. Tear-off 是否需要修正目标显示器坐标处理（O-4）；
3. 最大化／还原是否存在**可重复**的 `RestoreBounds` 持久化问题（O-5）。

若现状通过这些验收，**"现状可接受"就是合法且可封印的结论**；若不能，则依据失败证据
决定最小修复范围与必要的 schema 变更（且 O-1 的 v4 提案必须附实际失败案例）。

### 十·七 结束三问的当前答案（两轮之后）

1. **现有持久化几何能否满足混合 DPI 的可见性与尺寸契约？** **不能满足，而且与 DPI 无关**：
   DM-RP-01（完全越界）与 DM-RP-02（部分越界）在真实进程里证明"没有任何一层做可见性处理"；
   DM-B03 证明模型层连"越界"都无法表达；DM-RP-03 证明尺寸不会被缩小，且模型尺寸与真实
   窗口尺寸互不同步。**混合 DPI 的数值本身仍未验证**（本机 1 屏 96 DPI），不得据此宣称或
   否定混合 DPI 行为。**对 O-1 的直接影响**：失败案例确实存在，但三条规则都只依赖"当前
   可见工作区 + 矩形本身"，所以 v4 提案目前**没有证据要求**，纯几何基线够用。
2. **Tear-off 是否需要修正目标显示器坐标处理？** **需要**：DM-B01 证明换算口径取自事件携带
   的缩放（＝起始窗口所在屏），DM-B02 证明 tear-off 入口没有工作区钳制，DM-B03 证明恢复
   入口同样没有。O-4.1/O-4.3/O-4.4 与 O-3.2 未实现；跨屏真实数值误差的量化仍需 E2/E3。
3. **最大化／还原是否存在可重复的 `RestoreBounds` 持久化问题？** 在 E1 下**未复现，且这次
   是主动制造过渡帧之后仍未复现**：DM-RP-04 用背靠背 6 轮"最大化→还原"产生中间帧，落盘
   仍是还原后的正常几何（Debug 3 轮 + Release 2 轮数字逐位一致）；两条既有 D7-D 门禁另
   连续 3 轮复跑通过。ADR-010 §11.3 那次已指名的历史失败仍按"复验事实"保留，本轮结论
   不构成对其根因的判断；混合 DPI 屏上的过渡行为未验证。

### 十·八 由证据推出的最小修复范围（D10-B 记录时尚未授权；D10-C 已于同日授权并实施，见 §十一）

- **唯一被真实进程证实的用户可见缺陷**：越界浮动根恢复后不可见或不完全可见（DM-RP-01
  完全越界、DM-RP-02 部分越界）。修复面最小可收敛为"在宿主把几何应用到真实窗口的那一处，
  按 O-2 的五条规则做确定性钳制"，不需要新 schema 字段（与 O-1 接受 (A) 一致）；DM-B03
  解释了为什么只能落在宿主而不是模型（ADR-007 冻结"模型只含数字几何"）。
- **第二项**：Tear-off 的目标屏换算（O-4.1/O-4.3）与拖动期间的缩放口径（O-3.2）需要
  **指针所在显示器**的信息，而 §二 1 证明当前代码从不枚举屏幕。这是 D10-C 的第二项待裁决
  实现，也是唯一可能需要引入"屏幕查询"的地方——仍不需要引入屏幕身份持久化。
- **第三项（本轮新发现，范围很小）**：`CaptureBounds` 从不读回平台真实外框，所以模型尺寸
  与窗口实际尺寸会在两种情况下分叉——非客户边框（实测 +16/+39）与平台跟踪尺寸限制
  （实测 2960×1852 → 2580×1620）。是否在捕获时归一化属于 O-3.4"逻辑尺寸契约"的实现选择，
  须由用户在 D10-C 一并裁决；本轮只测量、不修改。
- 按 §九·二的硬限制，E2/E3/E4 的任何结论都必须来自实际接入第二显示器（或被允许改变本机
  缩放设置）后的复跑，不能由上述结果替代（O-6 第一/第二行的口径）。

### 十一·二 几何单位与字段语义（C-3 的实施前置，先于任何生产代码转换）

| 量 | 单位与语义 | 不得混用 |
| --- | --- | --- |
| `DockBounds.X` / `Y` | 窗口**外框**左上角的逻辑位置，数值 = 平台物理像素位置 ÷ **产生该几何的窗口当时**的 `RenderScaling`。不携带显示器身份（O-1），跨屏还原时按 O-2 策略重新定位。 | 不是物理像素；不是客户区原点 |
| `DockBounds.Width` / `Height` | 窗口**客户区**逻辑尺寸（DIP）。 | 不是平台外框尺寸（96 DPI 实测外框比客户区多 16×39 像素） |
| `DockFloatRoot.RestoreBounds` | 最大化之前的正常几何；持久化与 W3 摘要的唯一几何来源。 | 不得与 `Bounds` 合并 |
| `DockFloatRoot.Bounds` | 最近观测到的几何；最大化期间是平台给出的瞬态值。 | 不得当作恢复几何写盘 |
| `DockScreenArea.Bounds` / `WorkArea` | **物理像素**（虚拟桌面坐标），每个显示器携带自己的 `Scaling` 与主屏标记。 | 不得当作 DIP；不得用别的显示器缩放换算 |
| DIP↔像素换算 | 只在"给定某个具体显示器"时进行：`dip = px / screen.Scaling`，反之亦然；换算归宿主／窗口适配层。 | 禁止用主窗口或源窗口的 `RenderScaling` 换算目标屏几何（O-3.2／O-4.3） |

归一化规则（最小、可测、不改 schema）：

1. 捕获几何时，尺寸取平台**真实客户区**（Avalonia `ClientSize`），不再优先使用可能已经
   过期的 `Width`/`Height` 样式属性——DM-RP-03 证明被平台限制过的窗口会把旧值写回模型。
2. 恢复／首次显示时，宿主按 O-2 五条规则钳制**外框**（客户区 + 实测非客户边框），再把
   客户区几何写回宿主与模型；模型因此跟随用户实际看到的窗口。
3. 只有恢复与创建路径钳制；用户运行期拖动浮窗不改写其选择。
4. 不为这些差异扩大迁移范围：Schema v3 保持纯几何，屏幕身份与 DPI 元数据仍不落盘。
